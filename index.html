Turbo

Servidor web de alto rendimiento con interfaz visual para configuración en tiempo real.

Soporta dominios y subdominios multinivel, certificados SSL, direcciones alias, redirecciones, reescrituras, cabeceras (headers) o MIME personalizados. Adapta diferentes lenguajes de programación. Controla frecuencias, cantidades, tiempos y tamaños de las peticiones (requests).

Descripción

Turbo es un servidor web rápido que incluye una interfaz sencilla para configurarlo en tiempo real. Con ella se pueden organizar uno o más sitios web como dominios y subdominios multinivel; instalar y cambiar certificados SSL fácilmente, o crearlos y renovarlos con la integración a Certbot; adaptar distintos lenguajes de programación asignando preprocesadores a archivos con extensiones específicas; aplicar direcciones web alias, redirecciones de URL y reescrituras de URI; incluir cabeceras (headers) adicionales o modificar los tipos de contenido (MIME) según la extensión de los archivos; ajustar las frecuencias y cantidades de peticiones permitidas; y limitar los tiempos de procesamiento y los tamaños de las peticiones (requests). Además, incluye mitigación nativa contra el ataque DDoS HTTP/2 Rapid Reset (CVE-2023-44487).

Instalación

Linux
REQUISITOS
  • Conocimiento de servidores (VPS, bare metal...), sistema operativo Linux y línea de comandos Bash.
  • Distribución de Linux con systemd, nano y wget (comúnmente preinstalados).
  • Servidor con arquitectura de 64 bits y 128 MB de RAM disponible (mínimo recomendado).
  • Los ejecutables publicados son estáticos y no requieren bibliotecas del sistema. Si compila Turbo con cgo, el ejecutable requiere glibc 2.34 o superior.
  • Opcional: instalación de Certbot (instrucciones), para obtener y renovar certificados SSL. Con el servicio de systemd de abajo, instálelo con apt o pip: el de snap no funciona con él.
  1. Identificar la arquitectura del sistema operativo. Los ejecutables publicados son para 64 bits: x64 (x86-64, AMD64) y, en Linux, también ARM64 (AArch64); para otras arquitecturas, compile Turbo desde el código fuente siguiendo las instrucciones del repositorio oficial.

    Ejemplo:

    > uname -m
  2. Verificar que se tienen privilegios de usuario root (los comandos siguientes usan sudo).

    Ejemplo:

    > sudo -v
  3. Habilitar o desbloquear los puertos 80 y 443.

    Ejemplo (con ufw):

    > sudo ufw allow 80,443/tcp
    Si usa un proveedor de VPS (como AWS, Azure, Google Cloud, etc.), recuerde que también deberá abrir estos puertos desde la consola de administración en la nube.
  4. Crear un directorio (carpeta) para el servidor web.

    Ejemplo:

    > sudo mkdir /home/server/
  5. Descargar el ejecutable para 64 bits en un directorio temporal.

    Ejemplo:

    > cd $(mktemp -d)
> wget https://github.com/okzgn/turbo-go/releases/download/v2.4/turbo-linux-amd64
    En ARM64 (AArch64), descargue turbo-linux-arm64 (y use ese nombre en el paso siguiente). Compruebe la descarga con el archivo SHA256SUMS de la versión, descargado en el mismo directorio (sha256sum -c SHA256SUMS --ignore-missing).
  6. Instalar el ejecutable descargado en /usr/local/bin/, con el nombre turbo, de root y con permisos de lectura y ejecución. Queda fuera del directorio de sitios, donde los preprocesadores pueden escribir, así que no pueden sustituirlo.

    Ejemplo:

    > sudo install -o root -g root -m 0755 turbo-linux-amd64 /usr/local/bin/turbo
    Para pruebas, pasar de aquí a Cómo utilizar.
  7. Configurar el ejecutable como servicio (para ejecución en segundo plano). El servicio ejecuta Turbo con un usuario sin privilegios (turbo), que también ejecuta los preprocesadores y Certbot.

    Crear el usuario y darle la propiedad del directorio del servidor.

    Ejemplo:

    > sudo useradd --system --home-dir /home/server --shell /usr/sbin/nologin turbo
> sudo mkdir -p /home/server && sudo chown -R turbo:turbo /home/server
> sudo install -d -o root -g root -m 0755 /home/server/turbo.dev
> sudo install -d -o root -g root -m 0755 /etc/turbo
> sudo install -o root -g root -m 0600 /dev/null /etc/turbo/credenciales
> sudoedit /etc/turbo/credenciales
    En /etc/turbo/credenciales, escribir el usuario y la contraseña del panel, uno por línea: TURBO_USER=usuario y TURBO_PASSWORD=contraseña.
    Con este archivo, el panel nunca responde con las credenciales por defecto (Turbo/Admin), tampoco antes del primer acceso. Esas variables mandan sobre turbo.config en cada arranque: para cambiarlas, edite el archivo y reinicie el servicio; o, tras el primer acceso, cámbielas desde el panel, guarde la configuración y borre el archivo. La carpeta turbo.dev (de root) tiene que existir: el servicio no arranca sin ella, y así ningún preprocesador puede crearla para cambiar el panel.
    En el directorio /etc/systemd/system/, crear el archivo turbo.service.

    Ejemplo:

    > cd /etc/systemd/system/
> sudo nano turbo.service
    Escribir o pegar este contenido en el editor: 
    [Unit]
Description=Turbo
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=turbo
Group=turbo
WorkingDirectory=/home/server/
ExecStart=/usr/local/bin/turbo
EnvironmentFile=-/etc/turbo/credenciales
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/home/server/
ReadOnlyPaths=/home/server/turbo.dev
PrivateTmp=true
KillMode=mixed
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
    CAP_NET_BIND_SERVICE permite abrir los puertos 80 y 443 sin ser root, y Turbo la quita de lo que ejecuta (preprocesadores y Certbot no la heredan). Con ProtectSystem=strict, Turbo solo puede escribir en ReadWritePaths; la personalización de la interfaz (turbo.dev) es de solo lectura para el servicio, y PrivateTmp le da un /tmp propio (las subidas de archivos de PHP funcionan).

    Certbot trabaja en turbo.certificates, dentro del directorio de sitios. Con NoNewPrivileges, el Certbot de snap no funciona: instálelo con apt o con pip, también sus complementos DNS (python3-certbot-dns-*). Si usa una configuración de Certbot que escriba en otro directorio (como /etc/letsencrypt), añádalo a ReadWritePaths.

    PHP: guarde las sesiones dentro del directorio de sitios (session.save_path en php.ini), o añada su carpeta a ReadWritePaths.

    Modelo de confianza: los preprocesadores (PHP, etc.) y Certbot se ejecutan como el usuario turbo, así que un preprocesador puede modificar los sitios, turbo.config y los certificados (no el ejecutable, que es de root, ni turbo.dev), y leer el entorno de Turbo, con las credenciales de /etc/turbo/credenciales. Si un sitio no es de confianza, dele otro servidor, o un usuario propio detrás de un proxy.

    Detrás de un proxy, Turbo puede escuchar en otras direcciones añadiendo, en la sección [Service], líneas como Environment=TURBO_HTTP_ADDR=127.0.0.1:8080 y Environment=TURBO_HTTPS_ADDR=127.0.0.1:8443. Solo si las dos usan puertos por encima de 1023 deja de necesitar CAP_NET_BIND_SERVICE (sin TURBO_HTTPS_ADDR, HTTPS sigue en :443).

    Al parar el servicio (KillMode=mixed), systemd envía la señal solo a Turbo, que deja terminar hasta 10 s las peticiones en curso, también las de los preprocesadores.

    Si cambia el directorio de sitios a una carpeta fuera de /home/server, cambie también WorkingDirectory, ReadWritePaths y ReadOnlyPaths (la carpeta turbo.dev de ese directorio, de root).

    Si actualiza una instalación con el ejecutable en el directorio de sitios, instálelo como en el paso 6, cree turbo.dev y /etc/turbo/credenciales como arriba, sustituya el contenido de turbo.service por este y ejecute sudo systemctl daemon-reload y sudo systemctl restart turbo; después puede borrar el ejecutable anterior del directorio de sitios.
    Guardar el archivo turbo.service (Ctrl + O, Enter, Ctrl + X).

    Actualizar el sistema y habilitar el servicio.

    Ejemplo:

    > sudo systemctl daemon-reload
> sudo systemctl enable turbo
  8. Iniciar el servicio de Turbo.

    Ejemplo:

    > sudo systemctl start turbo
    Otros comandos:
    • Para detener momentáneamente el servicio, use el comando stop.
    • O use disable --now para detener completamente el servicio e impedir que se inicie con el sistema.
    • Los mensajes de Turbo (con nivel y hora) quedan en el registro del sistema (journal); para verlos, use journalctl -u turbo (con -f, para seguirlos en tiempo real).
    • La primera línea de cada arranque (msg=Inicio) dice la versión de Turbo, el commit del que se compiló y la versión de Go: compárela con las versiones afectadas de un aviso de seguridad.
Windows
REQUISITOS
  • Sistema operativo Windows 10 / Server 2016 o superior.
  • Equipo o servidor con arquitectura de 64 bits (x64, AMD64).
  • Privilegios de Administrador, solo para crear la regla del firewall de Windows. Ejecutar Turbo y abrir los puertos 80 y 443 no los requiere (Windows no tiene puertos privilegiados), siempre que ningún otro programa, como IIS, los use.
  • PowerShell instalado y actualizado, para ejecutar los siguientes comandos (ejemplos).
  1. Crear un directorio (carpeta) para el servidor web.

    Ejemplo:

    > mkdir C:\server\
  2. Descargar el ejecutable para Windows en el directorio anterior, con el nombre turbo.exe.

    Ejemplo:

    > Invoke-WebRequest https://github.com/okzgn/turbo-go/releases/download/v2.4/turbo-windows-x64.exe -OutFile C:\server\turbo.exe
  3. Habilitar o desbloquear los puertos 80 y 443 en el firewall de Windows.

    Ejemplo (ejecutar como Administrador):

    > New-NetFirewallRule -DisplayName "Turbo" -Direction Inbound -LocalPort 80,443 -Protocol TCP -Action Allow
    La regla es necesaria para recibir peticiones desde otros equipos, y crearla requiere Administrador (también desde el aviso del firewall que Windows puede mostrar la primera vez que se ejecuta Turbo).

    Si usa un proveedor de VPS (como AWS, Azure, Google Cloud, etc.), recuerde que también deberá abrir estos puertos desde la consola de administración en la nube.
  4. Ejecutar Turbo desde la terminal para permitir que el servidor escuche en los puertos 80 y 443 (no requiere Administrador).

    Ejemplo:

    > cd C:\server\
> .\turbo.exe
    Nota: En Windows, si cierra la ventana de la terminal, el servidor se detendrá. Para mantenerlo activo en segundo plano de forma permanente, puede configurar turbo.exe como un servicio de Windows utilizando herramientas gratuitas como WinSW (recomendado), NSSM o mediante el Programador de tareas.

Interfaz de configuración

Acceda a la interfaz (panel de control o administración, GUI) a través de una de las siguientes direcciones web.

Mediante la IP pública o el dominio web del servidor donde instaló Turbo.

Ejemplos:

http://11.22.33.44/admin:
http://dominio.com/admin:

O con localhost, desde el mismo equipo donde se ejecuta Turbo:

http://localhost/admin:

Allí, el formulario de acceso se verá como a continuación.

Ingrese con los datos por defecto:
Usuario: Turbo
Contraseña: Admin
IMPORTANTE
  • Cambie los datos de acceso por defecto desde la interfaz y guarde la configuración (Guardar configuración): el usuario y la contraseña (solo su hash, nunca en texto plano) se guardan en el archivo de configuración. Si no guarda la configuración, los datos de acceso vuelven a los anteriores al reiniciar el proceso, servicio o servidor (VPS, etc.), o al cerrar y volver a ejecutar Turbo.
  • Dé a la interfaz un host propio, que no sirva ningún sitio (por ejemplo admin.dominio.com, con su certificado, que puede obtener con Certificado del panel), en Dónde responde el panel. Sin él, la interfaz responde en los hosts de todos los sitios, y una página servida por Turbo en uno de ellos (subida por un cliente o comprometida) comparte su origen y podría usar la sesión del administrador. Turbo lo avisa al arrancar mientras no tenga un host propio, y también mientras se usen los datos de acceso por defecto.
  • HTTPS: por HTTP, los datos de acceso y la sesión viajan sin cifrar. Cuando un certificado cubre el host por el que se accede (el de Certificado del panel o el de un sitio) y HTTPS está abierto, la interfaz redirige a HTTPS las peticiones que le llegan por HTTP.
  • Intentos de acceso: el formulario envía los datos por POST, en el cuerpo de la petición (nunca en la URL). Tras 5 intentos fallidos desde la misma IP en 10 minutos, esa IP debe esperar antes de volver a intentarlo: 1 minuto, y después 2, 4, 8 y hasta 15. Una contraseña actual errónea en una opción que la pide cuenta como un intento fallido. En IPv6, todas las direcciones de un mismo bloque /64 cuentan como una sola IP.
  • Para cambiar los datos de acceso por defecto desde el binario, compile Turbo desde el código fuente, siguiendo las instrucciones del repositorio oficial de Turbo.
  • Variables de entorno para cambiar usuario, contraseña y directorio de sitios: TURBO_USER, TURBO_PASSWORD, TURBO_DIR (respectivamente). Si están definidas, TURBO_USER y TURBO_PASSWORD tienen prioridad sobre los datos guardados en la configuración.
  • Variables de entorno para las direcciones de escucha: TURBO_HTTP_ADDR y TURBO_HTTPS_ADDR (por defecto, :80 y :443). Aceptan host:puerto, :puerto o solo el puerto (por ejemplo, 127.0.0.1:8080), para usar Turbo detrás de un proxy (indique las dos: sin TURBO_HTTPS_ADDR, HTTPS sigue en :443 y necesita el permiso para puertos bajos). Si el valor no es válido, Turbo termina con un error. La redirección a HTTPS usa el puerto de TURBO_HTTPS_ADDR si no es 443.
  • Personalización de la interfaz (GUI): Puede sobrescribir los archivos del panel de administración en tiempo real creando una carpeta llamada turbo.dev en el directorio de sitios, con los archivos que quiera reemplazar (por ejemplo, turbo.dev/admin/#.html, turbo.dev/inside/#.html, o m.css, i.png, r.ttf y b.ttf en turbo.dev/admin/). Los archivos que falten se sirven desde la copia incluida en Turbo. Con el servicio de Linux, turbo.dev es de solo lectura para Turbo y sus preprocesadores: modifíquela con otro usuario (por ejemplo, con sudo). Implica conocer en profundidad la API (documentación de API).

Al ingresar, según la pantalla del dispositivo, la interfaz luce como en la imagen. Desde dentro podrá cambiar el usuario y la contraseña por defecto, o instalar certificados SSL para conectarse de forma segura. Cada inicio de sesión genera un token único, que se guarda en una cookie ligada a la IP desde la que se ingresó; la sesión se cierra automáticamente si el lapso de inactividad supera 10 minutos. Por HTTPS, la cookie es __Host-turbo_session, que los navegadores solo aceptan del propio host de la interfaz. Cambiar el usuario o la contraseña cierra todas las demás sesiones.

Continúe con la Documentación para conocer las opciones de la interfaz.

Documentación

    1. Configuración general

      Estas opciones requerirán la contraseña en el primer cuadro de diálogo (Certificado del panel, solo para eliminar el certificado). Si se usan por primera vez, ingrese la contraseña por defecto (vea la sección Interfaz de configuración).

      1. Cambiar usuario

        Establecerá el nuevo usuario de acceso a la interfaz.
      2. Cambiar contraseña

        Establecerá la nueva contraseña para la Configuración general y el acceso a la interfaz.
      3. Directorio de sitios

        Cambiará el directorio (carpeta) que el servidor web utiliza para leer, guardar o servir archivos de sitios web; el directorio debe existir. Por defecto, se usa el directorio de trabajo desde el que se ejecuta Turbo (en el servicio de Linux, WorkingDirectory) o el indicado en la variable de entorno TURBO_DIR. La ruta puede ser relativa al directorio de trabajo o usar la variable {TURBO_CURRENT_DIR}, y se guarda tal como se escribe (así la configuración se puede llevar a otro equipo).

        Si el nuevo directorio tiene un archivo de configuración, se aplica entero, y la respuesta dice qué cambia de Dónde responde el panel y de los datos de acceso (si el archivo no es JSON válido, el cambio se rechaza). Si no lo tiene, se conservan los ajustes en uso (configuración general, datos de acceso, IP denegadas, respuestas y reemplazos), que se escriben allí al guardar la configuración. Tras el cambio, la interfaz se recarga.

        Al guardar la configuración con otro directorio de sitios, Turbo deja en el directorio inicial un archivo de configuración que solo apunta al nuevo directorio, para leerlo desde allí al volver a ejecutarse (si había una configuración completa, antes guarda una copia: turbo.config.<fecha>.bak). Un archivo de configuración que solo apunta a su propio directorio impide arrancar: restaure una de sus copias .bak.
      4. Guardar configuración

        Crea un archivo (turbo.config) con toda la configuración del servidor web al momento de guardarse, incluidos el usuario y el hash de la contraseña, dentro del Directorio de sitios. El archivo se sustituye de una vez al guardar (si algo falla, queda el anterior); si era de una versión anterior de Turbo, antes se guarda una copia (turbo.config.v1.bak), y si no era JSON válido, otra (turbo.config.invalido.<fecha>.bak).

        Si al arrancar el archivo no es JSON válido (por ejemplo, tras editarlo a mano), Turbo no arranca, para no perder la configuración (ni volver a la contraseña por defecto): muestra el archivo, la línea y la columna del error, esa línea con una marca y las copias .bak que haya, para corregirlo o restaurar una. Tampoco arranca si el archivo no se puede leer, o si su Dónde responde el panel, su usuario o su contraseña no se pueden usar, y dice por qué. Si el archivo se rompe con Turbo en marcha, se mantiene la configuración en uso y el mismo mensaje va al registro.

        Si edita el archivo a mano con Turbo en marcha, Turbo lo revisa cada 30 segundos y, cuando cambia, lo aplica entero y de una vez: lo que ya no está en el archivo (una cabecera, un alias, un preprocesador, una IP denegada, etc.) deja de aplicarse, y los cambios hechos desde la interfaz y no guardados se pierden. Los certificados en uso siguen respondiendo. Las entradas se aplican en un orden fijo: cuando dos chocan (por ejemplo, Redirección a www y Redirección a raíz activas a la vez, la misma extensión escrita como PHP y php, o un alias en dos sitios), gana la primera (con las dos redirecciones, Redirección a raíz), con un aviso en el registro.
      5. Dónde responde el panel

        Limita la interfaz a los hosts y redes (CIDR, como 192.168.1.0/24) indicados, separados por comas (hasta 32); con los dos tipos, una petición necesita uno de los hosts y una de las redes. En los demás casos responde con estado 404. Vacío o * (por defecto): sin restricción. Configuración recomendada: un host propio para la interfaz, que no sirva ningún sitio, junto a las redes desde las que se administra; Turbo rechaza un host que sirva un sitio (directamente, por wildcard o como alias), y también un sitio, subdominio o alias nuevo que serviría ese host. El host lo elige el cliente: da a la interfaz un origen propio, pero solo las redes limitan quién accede.
      6. Certificado del panel

        Ejecuta Certbot, si está instalado, para solicitar un certificado SSL para los nombres de host de Dónde responde el panel (las direcciones IP quedan fuera). Requiere un e-mail y admite un adaptador DNS opcional (dns-<proveedor>); sin adaptador, Certbot valida por HTTP en esos hosts, donde Turbo responde a sus retos (/.well-known/acme-challenge/). El e-mail y el adaptador se guardan en la configuración. Mientras Certbot trabaja, la opción se muestra como (en proceso), y con el certificado en uso, como (activo); al hacer clic entonces, ofrece eliminarlo, con la contraseña actual (una errónea cuenta como un intento de acceso fallido). Turbo lo renueva como los de los sitios (vea Crear SSL).

        El certificado queda en la carpeta turbo.panel del Directorio de sitios (fullchain.pem y privkey.pem). También puede colocar esos archivos a mano: Turbo los vuelve a leer cuando cambian, pero no los renueva. La carpeta turbo.panel nunca es un sitio y no se sirve nada de ella.

        Con un certificado que cubre su host y HTTPS abierto, la interfaz redirige a HTTPS las peticiones por HTTP (estado 301, o 308 para conservar el método y el cuerpo de un POST), y por HTTPS, en un host de Dónde responde el panel, envía la cabecera Strict-Transport-Security (un año).

    2. Tiempo para cada petición

      Estas opciones se refieren a los tiempos permitidos para procesar o responder las peticiones recibidas por el servidor web. Se pueden especificar en milisegundos (ms), segundos (s) o minutos (m).

      1. Lectura de cabeceras

        Límite de tiempo para procesar los primeros datos estructurales o cabeceras (headers) de cada petición entrante. Superado el límite, se cierra la conexión con el emisor de la petición. Con 0s, se usa el valor de la Lectura total de petición. Valores admitidos: de 50 ms a 7,5 minutos, y no más de la mitad de la Lectura total de petición si esta tiene límite.
      2. Lectura total de petición

        Límite de tiempo para procesar contenidos que están a continuación de las cabeceras (headers) de cada petición entrante, como uploads de archivos. Este límite empieza con la Lectura de cabeceras. Superado el límite, se cierra la conexión con el emisor de la petición. Para evitar este límite, escriba: 0s. Valores admitidos: de 100 ms a 15 minutos.
      3. Escritura de respuesta

        Límite de tiempo para responder a cada petición procesada. Superado el límite, se corta la respuesta y se cierra la conexión con el receptor. También limita la ejecución de los preprocesadores. Si un preprocesador lo supera, el cliente recibe el estado 504, y se detienen el preprocesador y los procesos que haya lanzado (su grupo de procesos; en Windows, su Job Object), también si el cliente se desconecta antes. Para evitar este límite, escriba: 0s. Valores admitidos: de 100 ms a 30 minutos.
      4. Cierre de conexión inactiva

        Límite de tiempo para esperar la siguiente petición, sin cerrar la conexión, con el emisor de cada petición. Superado el límite, se cierra la conexión con el emisor. Con 0s, se usa el valor de la Lectura total de petición. Valores admitidos: de 100 ms a 5 minutos.

    3. Frecuencias de peticiones

      Estas opciones fijan lapsos de tiempo de referencia y el número de peticiones que, durante esos lapsos, el servidor web aceptará de cada emisor (IP). Cada emisor es una dirección IPv4 o, en IPv6, un bloque /64: todas sus direcciones cuentan como un solo emisor. Al superar el límite, el emisor queda bloqueado durante 5 segundos: sus peticiones reciben el estado 429 con la cabecera Retry-After (segundos restantes), y sus conexiones nuevas se cierran. El límite para el total de peticiones del servidor es otra opción, Límite global de peticiones, desactivada por defecto.

      1. Contador de peticiones por intervalo

        Lapso de tiempo referencial para contabilizar las peticiones recibidas de cada emisor, por cada lapso, hasta el límite de Peticiones máximas por intervalo. Este contador aumenta con cada petición y se reinicia al Tiempo de reinicio de contador. Se escribe el número en milisegundos sin ms, de 10 a 50000 (por defecto, 1000).
      2. Peticiones máximas por intervalo

        Número máximo de peticiones que se aceptan por cada Contador de peticiones por intervalo. Superado el límite, se bloquea temporalmente al emisor de peticiones. Se escribe un número mayor que 0 (por defecto, 100), no mayor que el Contador de peticiones por intervalo (en milisegundos) y tal que la división entera del Contador entre este número no supere 66, para que la interfaz siga funcionando (con 1000 ms, de 15 a 1000 peticiones).
      3. Tiempo de reinicio de contador

        Límite de tiempo para reiniciar el Contador de peticiones por intervalo para cada emisor de peticiones. Se escribe el número en milisegundos sin ms, de 1000 a 800000 (por defecto, 10000).
      4. Límite global de peticiones

        Número máximo de peticiones por segundo para todo el servidor, entre todos los emisores: por encima, las peticiones nuevas reciben el estado 503 con Retry-After: 1, sin bloquear a ninguna IP. Con 0 (por defecto), no hay límite global. Valores admitidos: 0, o de 10 a 1000000.

    4. Límites para cada petición

      Estas opciones especifican la cantidad de bytes que el servidor procesará de las peticiones entrantes, y cuántos preprocesadores pueden ejecutarse a la vez.

      1. Tamaño máximo de las URI

        Límite de longitud de la ruta del archivo, directorio (carpeta) o recurso que se solicita en cada petición. Superado el límite, se rechaza la petición con estado 414.
      2. Tamaño máximo de cabeceras

        Límite de bytes de cabeceras (headers) de cada petición. Superado el límite, se rechaza la petición con estado 431.
      3. Tamaño máximo de contenidos

        Límite de bytes de contenidos adjuntos a cada petición, como cargas (uploads) de archivos o cuerpos (bodies) de peticiones POST, entre otros. Por defecto, el servidor no procesa los contenidos adjuntos; el límite aplica siempre que sean utilizados (por la interfaz y por los preprocesadores, que no reciben más de este límite). Superado el límite, la petición a un preprocesador y la subida de archivos de la interfaz se rechazan con estado 413. Un contenido de tamaño desconocido (enviado por partes, chunked, o por HTTP/2 sin Content-Length) se lee entero antes de pasarlo al preprocesador, hasta este límite (en memoria hasta 1 MiB, y en un archivo temporal a partir de ahí), y el preprocesador lo recibe con su tamaño (CONTENT_LENGTH). En la subida de archivos de la interfaz cuenta, además del contenido, unos 600 bytes por archivo (lo que ocupa en memoria): un archivo de exactamente este tamaño no cabe, y si una subida lo supera, la salida es aumentarlo, porque cada subida sustituye la carpeta entera.
      4. Procesos CGI simultáneos

        Número máximo de preprocesadores (CGI) que pueden ejecutarse a la vez en todo el servidor. Una petición a un preprocesador que no encuentra hueco en 2 segundos recibe el estado 503 con Retry-After: 2. Con 0 (por defecto), el valor es automático: 4 por CPU, y al menos 16. Valores admitidos: 0, o de 1 a 100000.

    5. Agregar sitio

      Esta opción crea la estructura de directorios (carpetas) para cada sitio en el Directorio de sitios. Se puede agregar como localhost, IP (v4) o dirección web multinivel, con o sin comodines (wildcards). Las direcciones IPv6 no están soportadas. Al agregarlo, se verá en la interfaz, y al hacer clic en cualquier sitio agregado se mostrarán las opciones disponibles, las configuraciones de cada sitio y sus subdominios. En cada sitio, se incluye automáticamente el subdominio raíz, que equivale al mismo sitio, para configurarlo específicamente. No hay límite de sitios ni datos relativos a sitios. Los archivos públicos de cada sitio deben colocarse dentro de la subcarpeta creada automáticamente con el nombre @. El servidor traducirá a # físicamente en el disco los comodines * de los dominios con wildcards (p. ej. *.org, *.com.es).

      Ningún sitio (ni subdominio suyo) puede llamarse turbo.dev, turbo.panel, turbo.certificates, turbo.config, turbo.visits ni turbo.denials: son las carpetas y archivos que Turbo guarda en el Directorio de sitios. Tampoco pueden existir a la vez el sitio c.a.b y el subdominio c de a.b, que compartirían sus ajustes: si los dos aparecen en la configuración o en el disco, se queda el primero en orden, con un aviso en el registro. Un sitio no puede tener el nombre de un alias (vea Agregar alias).

      1. Validez de cada sitio

        Para que el servidor web responda a las peticiones de cada sitio agregado, este debe ser la dirección IP del servidor o un dominio o subdominio web real que apunte a la IP del servidor (mediante DNS). El servidor toma el nombre pedido (cabecera Host) en minúsculas, sin punto final y sin puerto, así que Dominio.COM. lo sirve el sitio dominio.com. Un nombre con caracteres que no sean letras, números, . o -, o con una parte que empieza o acaba en -, recibe el estado 404, también en los sitios con wildcards.

    6. Opciones para sitios y subdominios

      Opciones disponibles para cualquier sitio o subdominio.

      1. Agregar alias

        Añade direcciones que dirigen al mismo sitio o subdominio, sin redireccionar. Los alias añadidos se eliminan haciendo clic en cada uno. Por HTTPS, un alias necesita un certificado SSL que cubra su nombre; sin él, se sigue sirviendo por HTTP. Un alias no puede ser el nombre de un sitio o subdominio existente (lo taparía), y no se puede agregar un sitio con el nombre de un alias; si coinciden al cargar la configuración, gana el sitio y el alias se descarta, con un aviso en el registro.

      2. Crear SSL

        Ejecuta Certbot, si está instalado, para solicitar el certificado SSL para el sitio o subdominio, solo al hacer clic. Requiere un e-mail (para los avisos de Certbot) y admite un adaptador opcional, que solo puede ser un complemento DNS de Certbot (dns-<proveedor>, como dns-route53); sin adaptador, Certbot valida el dominio a través de la carpeta @ del sitio o subdominio (una petición a /.well-known/acme-challenge/ cuyo archivo está en @ se sirve tal cual, sin reescrituras ni redirecciones a www, raíz o HTTPS). Certbot se ejecutará en segundo plano, en la carpeta turbo.certificates del Directorio de sitios, y se mostrará el resultado o el estado del proceso (en curso mientras Certbot trabaja) haciendo clic en Respuesta SSL. Si el sitio o subdominio es wildcard, el certificado requiere un adaptador DNS (y el complemento de Certbot respectivo instalado).

        Turbo revisa cada día (y al iniciarse) los certificados que obtuvo con esta opción y los renueva automáticamente cuando les quedan menos de 30 días; si la Redirección a HTTPS está activa, el certificado renovado se usa sin reiniciar. Los certificados colocados manualmente no se renuevan.

        1. Borrar SSL

          Elimina los archivos del certificado SSL relativos al sitio o subdominio, tenga la antigüedad que tenga; si no hay certificado, no hace nada. Pide la contraseña actual (una errónea cuenta como un intento de acceso fallido). Si el certificado está activo por la opción Redirección a HTTPS (R. HTTPS), se mantendrá en memoria RAM hasta que se desactive, aunque esté expirado.
        2. Respuesta SSL

          Muestra la respuesta de Certbot relativa al certificado SSL solicitado del sitio o subdominio.
      3. Redirección a HTTPS (R. HTTPS)

        Activa la redirección al protocolo HTTPS de todas las visitas o peticiones por medio de HTTP del sitio o subdominio. Para activar esta opción, se necesita un certificado SSL previamente obtenido con Crear SSL; o colocar archivos válidos (fullchain.pem y privkey.pem) de certificados SSL en el directorio (carpeta) del sitio o subdominio para instalarlos al hacer clic. La instalación, actualización o desactivación de certificados SSL se realiza en tiempo real en la memoria RAM sin interrumpir las conexiones activas ni requerir el reinicio del servidor.

        Las conexiones HTTPS usan TLS 1.2 y 1.3. El certificado se elige por el nombre que pide el cliente (SNI): por HTTPS se rechazan las conexiones a nombres sin certificado y el acceso por IP. La redirección se hace al mismo nombre pedido, solo si un certificado lo cubre.

        1. Sin redirección a HTTPS (Sin r. HTTPS)

          Desinstala y borra de la memoria RAM el certificado SSL activo del sitio o subdominio, pero no elimina los archivos del certificado del directorio (carpeta) del sitio o subdominio.
        2. Colocación de archivos de certificado SSL

          Las ubicaciones correctas de archivos de certificados SSL en el directorio (carpeta) de cada sitio o subdominio son como las siguientes.

          Para sitios o subdominios raíz:
          /home/server/dominio.com/fullchain.pem
          /home/server/dominio.com/privkey.pem
          Para otros subdominios:
          /home/server/dominio.com/subdominio/fullchain.pem
          /home/server/dominio.com/subdominio/privkey.pem
      4. Subir archivos

        Elimina todo el contenido de la carpeta @ del sitio o subdominio (archivos y subcarpetas) y sube en su lugar los archivos o directorios seleccionados. Del directorio seleccionado se sube su contenido: el primer segmento de cada ruta (la carpeta elegida) se descarta. La respuesta informa de los archivos descartados: los que saldrían de @ y, en todos los sistemas, los nombres que Windows trata de forma especial (acabados en punto o espacio, como CON, NUL o COM1, o con ~ seguido de un número, como los nombres cortos INDEX~1.PHP, o con un carácter que Windows no admite: < > " | ? * o de control), los que los sistemas de archivos no admiten por largos (un nombre de más de 255 bytes o una ruta de más de 1024), y, de un archivo y una carpeta con el mismo nombre (a y a/b), el segundo. La subida está sujeta al Tamaño máximo de contenidos y admite hasta 10000 archivos. Los certificados SSL no se ven afectados, ya que se guardan separados de los archivos públicos. La carpeta @ se sustituye de una vez al terminar: si algo falla, o se descartan todos los archivos, queda como estaba. Pide la contraseña actual (una errónea cuenta como un intento de acceso fallido).

      5. Borrar sitio/subdominio

        Elimina todo lo relacionado con un sitio o subdominio, incluido el directorio (carpeta). Si es sitio, los subdominios también se eliminarán con toda la información relacionada. Si es subdominio raíz, esta opción se mostrará como Borrar sitio, ya que equivale al mismo sitio. Pide la contraseña actual (una errónea cuenta como un intento de acceso fallido). En cualquier caso, no se harán cambios en el archivo de configuración hasta que se utilice la opción Guardar configuración.

    7. Opciones para sitios o subdominios raíz

      Estas opciones son únicamente para sitios o subdominios raíz: se configuran allí, aunque Redirección a raíz actúa sobre las visitas al subdominio www. La interfaz no las muestra en los demás subdominios.

      1. Redirección a www (R. www)

        Redirige automáticamente hacia el subdominio www las visitas o peticiones al subdominio raíz. Si esta opción se activa, la redirección contraria no podrá activarse. Ejemplo:
        Visita: https://dominio.com
        Redirección: https://www.dominio.com
        1. Sin redirección a www (Sin r. www)

          Desactiva la redirección automática al subdominio www desde el subdominio raíz.
      2. Redirección a raíz (R. raíz)

        Redirige automáticamente hacia el subdominio raíz las visitas o peticiones al subdominio www. Si esta opción se activa, la redirección contraria no podrá activarse. Ejemplo:
        Visita: https://www.dominio.com
        Redirección: https://dominio.com
        1. Sin redirección a raíz (Sin r. raíz)

          Desactiva la redirección automática al subdominio raíz desde el subdominio www.

    8. Agregar subdominio

      Esta opción crea la estructura de directorios (carpetas) de cada subdominio dentro del directorio del sitio al que pertenece, a excepción del subdominio raíz. Se puede agregar como multinivel (nivel3.nivel2.subdominio) y puede incluir wildcards. Un subdominio sin comodín sirve solo su propio host: api sirve api.ejemplo.com, y los niveles más profundos (x.api.ejemplo.com) los sirve un comodín, *.api (o el * del sitio). Al agregarlo, se verá en la interfaz, y al hacer clic en cualquier subdominio agregado se mostrarán las opciones disponibles y las configuraciones de cada subdominio. No hay límite de subdominios ni datos relativos a subdominios. Los archivos públicos de cada subdominio deben colocarse dentro de la subcarpeta creada automáticamente con el nombre @. El servidor traducirá a # físicamente en el disco los comodines * de los subdominios con wildcards (p. ej. *.ejemplo.com, *.area.dominio.org).

    9. Opciones de subdominios

      Opciones disponibles para cualquier subdominio.

      1. Agregar MIME

        Reemplaza la cabecera (header) Content-Type por defecto de los archivos del subdominio que tengan la extensión especificada, por el contenido ingresado. Es posible especificar una extensión vacía para referirse a archivos sin extensión (como en la imagen); un punto solo (.) no equivale a "sin extensión" y se rechaza.

      2. Agregar cabecera

        Agrega la cabecera (header) con el nombre y el contenido especificados a las respuestas de los archivos y preprocesadores del subdominio (no a las respuestas 404 ni a las redirecciones de reescrituras, HTTPS o www). El nombre admite letras, números, - y ., hasta 48 caracteres; el contenido, hasta 512.

      3. Agregar reescritura

        Agrega una reescritura de la ruta de archivo, directorio o recurso (URI) determinado, para tratarlo internamente como otra ruta de archivo, directorio o recurso especificado sin redireccionarlo. No es obligatorio ingresar una URI existente. La URI de origen empieza por / (hasta 128 caracteres), y el destino, por /, http:// o https:// (hasta 512). Se puede acceder a la información de la primera URI y datos del sitio y subdominio con palabras clave (útil en sitios o subdominios con wildcards y para preprocesadores); una palabra clave desconocida se rechaza (en el archivo de configuración, la reescritura se descarta con un aviso en el registro). La URI de origen se compara con la ruta pedida ya decodificada (/a b coincide con /a%20b), y el destino también se trata como una ruta URL (un % literal se escribe %25). Si, tras reemplazar las palabras clave, la ruta sale de la carpeta @ o contiene \, se responde con estado 404.

        Para redireccionar, ingrese un destino que empiece por http:// o https:// (en mayúsculas o minúsculas; se guarda en minúsculas) seguido de un host, escrito o dado por una palabra clave: se responde con estado 302. Un destino sin host (como https:// solo) se rechaza, y si la palabra clave del host no da ningún valor al responder, se responde con estado 500. Si el destino tiene ruta o consulta (query string), se redirige exactamente a ese destino; si es solo un dominio, se le añade la URI original.

        1. Información accesible

          Al incluir palabras clave en las reescrituras, se reemplazarán por la información respectiva. Se escriben de la siguiente manera:
          {PALABRA_CLAVE}
          Los valores de FIRST_REQUEST, DIR, FILE, EXT, REWRITE y REWRITE_COMPLEMENT salen de la ruta pedida ya decodificada, y los de FIRST_QUERY, de su consulta. Cada valor se inserta codificado según dónde va en el destino: en la ruta, por segmentos, sin tocar /; en la consulta (query string), como un valor (por ejemplo, / se convierte en %2F); en el host, de forma que no pueda cambiar la URL. Por ejemplo, con el origen /blog/ y el destino /new/{REWRITE_COMPLEMENT}, /blog/a/b?x=1 pasa a /new/a/b?x=1. Cuando se accede por un alias de un sitio wildcard, SUBDOMAIN y SITE contienen el patrón (con *); los nombres del alias están en las palabras FIRST_.

          Palabras clave disponibles:
          1. TURBO_CURRENT_DIR

            Contiene la ruta desde donde se sirven los sitios web.
          2. WILDCARD_SITE

            Contiene la dirección web completa (con subdominio y dominio) del sitio wildcard al que pertenece.
          3. WILDCARD_DOMAIN

            Contiene el dominio web del sitio wildcard al que pertenece.
          4. WILDCARD_SUBDOMAIN

            Contiene el subdominio web del sitio wildcard al que pertenece.
          5. DOMAIN

            Contiene el dominio web del sitio al que pertenece.
          6. SUBDOMAIN

            Contiene el subdominio web del sitio al que pertenece.
          7. SITE

            Contiene la dirección web completa (con subdominio y dominio) del sitio al que pertenece.
          8. FIRST_DOMAIN

            Contiene el dominio web alias al que pertenece.
          9. FIRST_SUBDOMAIN

            Contiene el subdominio web alias al que pertenece.
          10. FIRST_SITE

            Contiene la dirección web alias completa (con subdominio y dominio) a la que pertenece.
          11. FIRST_REQUEST

            Contiene la ruta o URI completa que se reescribió.
          12. FIRST_QUERY

            Contiene los parámetros de consulta (query string) de la URI que se reescribió.
          13. DIR

            Contiene el directorio (carpeta) de la URI que se reescribió.
          14. FILE

            Contiene el nombre del archivo que se reescribió.
          15. EXT

            Contiene la extensión del archivo que se reescribió.
          16. REWRITE

            Contiene la URI de origen de la reescritura que coincidió.
          17. REWRITE_COMPLEMENT

            Contiene el resto de la URI pedida tras la URI de origen de la reescritura (ruta y parámetros de consulta). En la ruta del destino, contiene solo el resto de la ruta, y los parámetros de consulta de la petición se añaden a los del destino.
      4. Agregar preprocesador

        Asigna el preprocesador determinado para todos los archivos con la extensión especificada del subdominio, sin distinguir mayúsculas (.PHP también se ejecuta como .php). El preprocesador debe procesar y responder, mediante CGI y las variables de entorno respectivas, las peticiones de los archivos con la extensión especificada.

        Para preprocesadores como php-cgi, Turbo inyecta automáticamente la variable de entorno REDIRECT_STATUS=CGI, permitiendo ejecutar scripts de PHP directamente sin modificar el archivo php.ini. Con la unidad systemd de referencia, la carpeta de sesiones por defecto de PHP (/var/lib/php/sessions) es de solo lectura: indique en session.save_path una carpeta dentro de la de los sitios.

        Es Turbo quien delimita la respuesta: de la que escribe el preprocesador se descartan las cabeceras sobre la conexión (Transfer-Encoding, Connection, Keep-Alive, Upgrade…), un Content-Length repetido y las cabeceras con caracteres de control.

        La ruta del preprocesador admite hasta 128 caracteres y debe existir al agregarlo; el prefijo dx> no está disponible. Como un preprocesador ejecuta programas en el servidor, esta opción pide la contraseña actual (una errónea cuenta como un intento de acceso fallido). Borrarlo (la X junto a él) también la pide: sin su preprocesador, los archivos de esa extensión se servirían como texto, con su código fuente. Si más tarde el binario no existe (por ejemplo, al cargar la configuración guardada), los archivos con esa extensión responden con estado 500 en lugar de servirse. Lo mismo ocurre con un preprocesador del archivo de configuración que no se puede usar (ruta vacía o demasiado larga, extensión incorrecta, otro prefijo, ejecutable inexistente): se conserva, con un aviso en el registro, y su extensión responde con estado 500; los archivos nunca se sirven como texto.

        Los preprocesadores que se ejecutan a la vez están limitados por Procesos CGI simultáneos, y su tiempo, por Escritura de respuesta.

        IMPORTANTE: Si la configuración para preprocesar los archivos no está activa en el subdominio, los archivos para uso dinámico (preprocesados, usualmente código) serán servidos como estáticos (texto plano, etc., dependiendo del MIME), lo que puede comprometer la confidencialidad de estos archivos y su código fuente.

      5. Agregar índice

        Agrega el archivo por defecto para responder a peticiones (requests) de directorios (carpetas). Es necesario que el archivo especificado exista en cada directorio. Si se especifica más de uno, se prueban en el orden en que se agregaron. Los sitios y subdominios nuevos incluyen index.html por defecto. Una petición cuya ruta termina en /index.html se redirige (estado 301) a su directorio (./).

    10. Archivos de registros (logs)

      Para registrar los accesos rechazados por el limitador de frecuencia, cree un archivo accesible llamado turbo.denials, y para registrar cada acceso a cada archivo o ruta en el servidor, cree otro archivo llamado turbo.visits, en el Directorio de sitios. Turbo solo escribe en estos archivos si existen; los detecta (o deja de usarlos al borrarlos) en su revisión periódica, cada 30 segundos. Ya que pueden aumentar mucho de tamaño, no cree estos archivos si no necesita registros. Los demás mensajes de Turbo se muestran en la salida estándar (stdout) o en la consola, con nivel (INFO, WARN, ERROR) y fecha y hora; con el servicio de Linux, quedan en el journal (journalctl -u turbo).

      turbo.visits no registra las peticiones rechazadas por los limitadores (429, 503), las conexiones cerradas al llegar desde una IP bloqueada, ni las peticiones mal formadas o demasiado grandes que se rechazan antes de procesarlas (400, 414, 431); los bloqueos, también los de intentos de acceso fallidos, quedan en turbo.denials.

      Privacidad: turbo.visits registra, por cada petición que procesa, la IP del emisor, la fecha (timestamp UNIX), el método, el host y la URI completa, con sus parámetros de consulta, incluidas las peticiones a la interfaz (la interfaz envía sus datos, como la contraseña actual, en el cuerpo de la petición, que no se registra). Un cliente de la API que ponga la contraseña u otros datos sensibles en la URL los dejaría en este archivo: debe enviarlos en el cuerpo, como la interfaz. La sesión de la interfaz no aparece en él, porque viaja en una cookie. Trate este archivo como información personal y sensible: restrinja su acceso y bórrelo o rótelo según sus necesidades.

    11. Agregar IP denegada

      Permite bloquear de forma manual e inmediata direcciones IP específicas (IPv4 o IPv6). Se ingresa la dirección IP y la fecha en formato timestamp UNIX hasta la cual la IP permanecerá bloqueada. Mientras dure el bloqueo, sus peticiones reciben el estado 429 (con Retry-After) y sus conexiones nuevas se cierran. No se pueden bloquear las IP de localhost ni la IP desde la que se usa la interfaz. A diferencia de los límites de Frecuencias de peticiones, se bloquea exactamente la dirección ingresada (en IPv6, no todo su bloque /64). Transcurrido ese tiempo, el servidor la desbloquea automáticamente. Para eliminar el bloqueo manualmente antes de la fecha, haga clic sobre la X de la IP en la lista.

    12. Agregar respuesta a código HTTP

      Permite personalizar la respuesta o plantilla de texto/HTML devuelta por el servidor cuando ocurre un código de estado de error HTTP determinado (códigos entre 400 y 599, o 0 para la respuesta general por defecto). Se utiliza la etiqueta {TURBO_RESPONSE_CODE} para incluir dinámicamente el código de error en la respuesta. Si la plantilla empieza por <, se sirve como HTML; si no, como texto plano, donde \n es un salto de línea. Admite hasta 2048 caracteres.

    13. Agregar reemplazo de caracteres

      Permite definir reglas globales de sustitución de caracteres especiales en los valores que la interfaz envía al servidor (reescrituras, MIME, cabeceras, etc.); no se aplican a las URI de las peticiones que recibe el servidor. Sustituye caracteres que puedan causar conflictos con delimitadores de URL (por ejemplo: ; por -.-, # por -,-, o & por -_-) por cadenas seguras para enviarlos, y Turbo los restituye al recibirlos, en todos los valores. Ningún valor puede contener caracteres de control (las plantillas de respuesta sí admiten saltos de línea y tabuladores).
