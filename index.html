High-performance web server with a visual interface for real-time configuration.

Supports multi-level domains and subdomains, SSL certificates, aliases, redirections, rewrites, and custom headers or MIME types. Adapts to different programming languages. Controls the rate, count, time and size of requests.

Description

Turbo is a fast web server with a simple interface to configure it in real time. With it you can organize one or more websites as multi-level domains and subdomains; install and change SSL certificates easily, or issue and renew them through its Certbot integration; adapt different programming languages by assigning preprocessors to files with specific extensions; set up aliases, URL redirections and URI rewrites; add headers or change the content types (MIME) by file extension; adjust the allowed request rates and counts; and limit the processing times and sizes of requests. Over HTTPS it uses TLS 1.3, and TLS 1.2 only with ECDHE and AES-GCM or ChaCha20-Poly1305. It also mitigates the HTTP/2 Rapid Reset DDoS attack (CVE-2023-44487): Go's protection plus Turbo's own limit of RST_STREAM frames that cancel an open stream (200 per second and connection).

The changes of each version, and how to upgrade, are in the changelog. This page is also available in Spanish.

Installation

If you upgrade from an earlier version (v2.4.1, v2.4 or v2.3.rc3), first read the upgrading section for your version in the changelog, and back up the sites folder, turbo.config included. v2.4.2 fixes security issues: upgrade as soon as possible. Among its breaking changes, the default password (Admin) signs in only from the machine itself (see Configuration interface): set your own password before you upgrade, or TURBO_PASSWORD.
Linux
REQUIREMENTS
  • Knowledge of servers (VPS, bare metal...), the Linux operating system and the Bash command line.
  • A Linux distribution with systemd, nano and wget (usually preinstalled).
  • A 64-bit server with 128 MB of free RAM (recommended minimum).
  • The published binaries are static and need no system libraries. If you build Turbo with cgo, the binary needs glibc 2.34 or later. Building Turbo from the source needs Go 1.26.10 (an older Go downloads it).
  • Optional: Certbot (instructions), to issue and renew SSL certificates. With the systemd service below, install it with apt or pip: the snap one doesn't work with it.
  1. Identify the architecture of the operating system. The published binaries are 64-bit: x64 (x86-64, AMD64) and, on Linux, also ARM64 (AArch64); for other architectures, build Turbo from the source following the instructions in the official repository.

    Example:

    > uname -m
  2. Check that you have root user privileges (the next commands use sudo).

    Example:

    > sudo -v
  3. Open ports 80 and 443.

    Example (with ufw):

    > sudo ufw allow 80,443/tcp
    If you use a VPS provider (such as AWS, Azure, Google Cloud, etc.), remember to open these ports in its cloud console too.
  4. Create a directory (folder) for the web server.

    Example:

    > sudo mkdir /home/server/
  5. Download the 64-bit binary into a temporary directory.

    Example:

    > cd $(mktemp -d)
> wget https://github.com/okzgn/turbo-go/releases/download/v2.4.2/turbo-linux-amd64
    On ARM64 (AArch64), download turbo-linux-arm64 (and use that name in the next step). Check the download with the SHA256SUMS file of the release, downloaded into the same directory (sha256sum -c --ignore-missing SHA256SUMS: --ignore-missing checks only the binaries you downloaded).
  6. Install the downloaded binary in /usr/local/bin/, named turbo, owned by root, with read and execute permissions. It stays outside the sites directory, where the preprocessors can write, so they can't replace it.

    Example:

    > sudo install -o root -g root -m 0755 turbo-linux-amd64 /usr/local/bin/turbo
    For testing, go on from here to Getting started.
  7. Set up the binary as a service (to run in the background). The service runs Turbo as an unprivileged user (turbo), which also runs the preprocessors and Certbot.

    Create the user and give it the server directory, without permissions for other users.

    Example:

    > sudo useradd --system --home-dir /home/server --shell /usr/sbin/nologin turbo
> sudo mkdir -p /home/server && sudo chown -R turbo:turbo /home/server && sudo chmod 0750 /home/server
> sudo install -d -o root -g root -m 0755 /home/server/turbo.dev
> sudo install -d -o root -g root -m 0755 /etc/turbo
> sudo install -o root -g root -m 0600 /dev/null /etc/turbo/credentials
> sudoedit /etc/turbo/credentials
    In /etc/turbo/credentials, write the user and the password of the panel, one per line: TURBO_USER=user and TURBO_PASSWORD=password (12 to 64 bytes).
    With this file, the panel never answers with the default credentials (Turbo/Admin), not even before the first login; without it, the default password signs in only from the machine itself (through an SSH tunnel, for example). Those variables override turbo.config at every start: to change them, edit the file and restart the service (a change from the panel lasts until the next start); or, after the first login, change them from the panel, save the configuration and delete the file. The turbo.dev folder (owned by root) has to exist: the service doesn't start without it, so no preprocessor can create it to change the panel.
    In the /etc/systemd/system/ directory, create the turbo.service file.

    Example:

    > cd /etc/systemd/system/
> sudo nano turbo.service
    Type or paste this content in the editor (the repository's reference unit, deploy/turbo.service, without its comments): 
    [Unit]
Description=Turbo
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=turbo
Group=turbo
WorkingDirectory=/home/server/
ExecStart=/usr/local/bin/turbo
EnvironmentFile=-/etc/turbo/credentials
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/home/server/
ReadOnlyPaths=/home/server/turbo.dev
PrivateTmp=true
UMask=0027
ProtectHome=tmpfs
BindPaths=/home/server
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectKernelLogs=true
ProtectControlGroups=true
ProtectClock=true
ProtectHostname=true
ProtectProc=invisible
RestrictNamespaces=true
RestrictRealtime=true
RestrictSUIDSGID=true
LockPersonality=true
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK
SystemCallArchitectures=native
SystemCallFilter=@system-service
SystemCallFilter=capget capset prctl
SystemCallErrorNumber=EPERM
KillMode=mixed
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
    CAP_NET_BIND_SERVICE lets Turbo open ports 80 and 443 without being root, and Turbo removes it from what it runs (the preprocessors and Certbot don't inherit it). With ProtectSystem=strict, Turbo can only write in ReadWritePaths; the interface customization (turbo.dev) is read-only for the service, and PrivateTmp gives it a /tmp of its own (PHP file uploads work).

    Hardening: the rest of the lines limit what a preprocessor that has been taken over can do on the machine: it sees no other home folder than /home/server (ProtectHome with BindPaths) and no devices but the pseudo ones, and can't create namespaces, load modules, change the clock, the host name or the kernel settings, use set-user-ID files or sockets other than Unix, IPv4, IPv6 and netlink, nor make system calls outside those of a service (@system-service, plus capget, capset and prctl, which Turbo uses to clear the capabilities of what it runs). Files are created without permissions for other users (UMask=0027). If a PHP extension needs more (a system call, an address family), add it with a drop-in (systemctl edit turbo) rather than removing the whole line.

    Certbot works in turbo.certificates, inside the sites directory. With NoNewPrivileges, the snap Certbot doesn't work: install it with apt or with pip, its DNS plugins too (python3-certbot-dns-*). If a Certbot configuration of yours writes to another directory (such as /etc/letsencrypt), add it to ReadWritePaths.

    PHP: keep the sessions inside the sites directory (session.save_path in php.ini), or add their folder to ReadWritePaths.

    Trust model: the preprocessors (PHP, etc.) and Certbot run as the turbo user, so a preprocessor can modify the sites, turbo.config and the certificates (not the binary, owned by root, nor turbo.dev), and read Turbo's environment, with the credentials of /etc/turbo/credentials (Certbot and its hooks get it without the TURBO_* variables). If a site is not trusted, give it another server, or a user of its own behind a proxy.

    Behind a proxy, Turbo can listen on other addresses by adding, in the [Service] section, lines such as Environment=TURBO_HTTP_ADDR=127.0.0.1:8080 and Environment=TURBO_HTTPS_ADDR=127.0.0.1:8443. Only if both use ports above 1023 does it no longer need CAP_NET_BIND_SERVICE (without TURBO_HTTPS_ADDR, HTTPS stays on :443). A proxy on the same machine must send X-Forwarded-For, Forwarded or X-Real-IP: otherwise Turbo takes its clients for the machine itself (see Configuration interface).

    On stop (KillMode=mixed), systemd sends the signal only to Turbo, which lets the requests in progress, the preprocessors' included, finish for up to 10 s.

    If you change the sites directory to a folder outside /home/server, also change WorkingDirectory, BindPaths, ReadWritePaths and ReadOnlyPaths (the turbo.dev folder of that directory, owned by root).

    If you upgrade an earlier installation, install the binary as in step 6, create turbo.dev and /etc/turbo/credentials as above if you don't have them, set /home/server to 0750, replace the content of turbo.service with this one and run sudo systemctl daemon-reload and sudo systemctl restart turbo; then check that your preprocessors still work and, if the old binary was in the sites directory, delete it from there.
    Save the turbo.service file (Ctrl + O, Enter, Ctrl + X).

    Reload systemd and enable the service.

    Example:

    > sudo systemctl daemon-reload
> sudo systemctl enable turbo
  8. Start the Turbo service.

    Example:

    > sudo systemctl start turbo
    Other commands:
    • To stop the service for a while, use the stop command.
    • Or use disable --now to stop the service completely and keep it from starting with the system.
    • Turbo's messages (with level and time) go to the system log (journal); to see them, use journalctl -u turbo (with -f, to follow them in real time).
    • The first line of each start (msg=Starting) says the version of Turbo, the commit it was built from and the Go version, for example version=v2.4.2 commit=… go=go1.26.10 (journalctl -u turbo | grep msg=Starting): compare it with the affected versions of a security advisory.
Windows
REQUIREMENTS
  • Windows 10 / Server 2016 or later.
  • A 64-bit computer or server (x64, AMD64).
  • Administrator rights, only to create the Windows Firewall rule. Running Turbo and opening ports 80 and 443 doesn't need them (Windows has no privileged ports), as long as no other program, such as IIS, uses them.
  • PowerShell, installed and up to date, to run the following commands (examples).
  1. Create a directory (folder) for the web server.

    Example:

    > mkdir C:\server\
  2. Download the Windows binary into the directory above, named turbo.exe.

    Example:

    > Invoke-WebRequest https://github.com/okzgn/turbo-go/releases/download/v2.4.2/turbo-windows-x64.exe -OutFile C:\server\turbo.exe
    Check the download with the checksum in Downloads (Get-FileHash C:\server\turbo.exe).
  3. Open ports 80 and 443 in the Windows Firewall.

    Example (run as Administrator):

    > New-NetFirewallRule -DisplayName "Turbo" -Direction Inbound -LocalPort 80,443 -Protocol TCP -Action Allow
    The rule is needed to receive requests from other machines, and creating it needs Administrator rights (also from the firewall dialog that Windows may show the first time Turbo runs).

    If you use a VPS provider (such as AWS, Azure, Google Cloud, etc.), remember to open these ports in its cloud console too.
  4. Run Turbo from the terminal to let the server listen on ports 80 and 443 (no Administrator rights needed).

    Example:

    > cd C:\server\
> .\turbo.exe
    Note: on Windows, closing the terminal window stops the server. To keep it running in the background, you can set up turbo.exe as a Windows service with free tools such as WinSW (recommended) or NSSM, or with the Task Scheduler.

    On Windows, the 0600 permissions with which Turbo writes turbo.config, its copies and the certificate keys have no effect: the files get the permissions (ACL) of their folder, so restrict who can read the sites directory.

Getting started

Linux
IMPORTANT
At least, complete the installation up to step 6.
IF YOU:
  • Don't install or start Turbo as a service (step 7 or 8).
  • Are testing.
Run Turbo to go on.

Example:

> cd /home/server/
> sudo /usr/local/bin/turbo

Example, running WITHOUT sudo (on ports above 1023):

> cd /home/server/
> TURBO_HTTP_ADDR=:8080 TURBO_HTTPS_ADDR=:8443 /usr/local/bin/turbo

Configuration interface

Open the interface (control or admin panel, GUI) at one of the following addresses.

With localhost, from the same machine where Turbo runs (the only place where the default password works):

http://localhost/admin:Local

Or through the public IP or the domain of the server where you installed Turbo, once it has a password of your own.

Examples:

http://11.22.33.44/admin:IP
http://example.com/admin:Domain

There, the sign-in form looks like this.

Sign in with the default credentials:
User: Turbo
Password: Admin
IMPORTANT
  • The default password works only from the machine itself: while Admin is the panel's password, it opens a session only from a loopback address (127.0.0.1, ::1), to a host that is localhost, a loopback address or a host of Where the panel answers (a page of another name that resolves to this machine can't use it), and without the headers a proxy sends (Forwarded, X-Forwarded-For, X-Real-IP, Via…). From elsewhere, the sign-in form says why, without counting it as a failed attempt. On a remote server, use an SSH tunnel to Turbo's HTTP port: 
    > ssh -L 8080:localhost:80 user@server
    and open http://localhost:8080/admin: on your computer. Or set TURBO_PASSWORD first (see step 7 of the installation). A proxy on the same machine must send X-Forwarded-For (in nginx, proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;), Forwarded or X-Real-IP, or Turbo takes its clients for the machine itself.
  • Change the default credentials from the interface and save the configuration (Save configuration): the user and the password (only its PBKDF2 hash, never in plain text) are saved in the configuration file. A new password has 12 to 64 bytes. If you don't save the configuration, the credentials go back to the previous ones when the process, the service or the server (VPS, etc.) restarts, or when Turbo is closed and run again. While the default credentials are in use, Turbo warns about it at startup.
  • Give the interface a host of its own, one that serves no site (for example admin.example.com, with its certificate, which you can get with Panel certificate), in Where the panel answers. Without it, the interface answers on the hosts of every site, and a page served by Turbo on one of them (uploaded by a customer, or compromised) shares its origin and could use the administrator's session. Turbo warns about it at startup while it has no host of its own, and the option shows (warning: no host of its own).
  • HTTPS: over HTTP, the credentials and the session travel in clear text. When a certificate covers the host you use (the one of Panel certificate or a site's) and HTTPS is open, the interface redirects to HTTPS the requests it gets over HTTP.
  • Sign-in attempts: the form sends the credentials by POST, in the request body (never in the URL). After 5 failed attempts from the same IP within 10 minutes, that IP must wait before trying again: 1 minute, then 2, 4, 8 and up to 15. In IPv6, all the addresses of the same /64 count as one IP, and the /64s of the same /48 also share a limit of 20 failed attempts, which a client that signed in correctly in the last 12 hours skips. A sign-in that the browser marks as sent from another page (another origin) is refused, without counting.
  • Current password: the options that ask for it (all of General settings, the times, rates and limits, and those noted in each option) count the wrong ones per session: the fifth in a session closes it, and you have to sign in again.
  • To change the default credentials in the binary, build Turbo from the source, following the instructions in Turbo's official repository.
  • Environment variables for the user, the password and the sites directory: TURBO_USER, TURBO_PASSWORD and TURBO_DIR. When set, TURBO_USER and TURBO_PASSWORD take priority over the credentials saved in the configuration. Set but empty, Turbo doesn't start, nor with a TURBO_USER of more than 24 characters, a TURBO_PASSWORD of more than 64 bytes, or control characters; with fewer than 12 bytes, or with the password Admin, Turbo warns at startup.
  • Environment variables for the listening addresses: TURBO_HTTP_ADDR and TURBO_HTTPS_ADDR (by default, :80 and :443). They take host:port, :port or just the port (for example, 127.0.0.1:8080), to run Turbo behind a proxy (set both: without TURBO_HTTPS_ADDR, HTTPS stays on :443 and needs the permission for low ports). If the value isn't valid, Turbo exits with an error. The redirection to HTTPS uses the port of TURBO_HTTPS_ADDR when it isn't 443.
  • Behind a proxy, Turbo sees the proxy's address as the client IP: the per-IP limits, the denied IPs, the logs, the networks of Where the panel answers and the session bound to an IP see only the proxy, and 5 failed attempts through it lock every client out of the interface, the administrator included, for up to 15 minutes.
  • Interface (GUI) customization: you can replace the files of the admin panel in real time by creating a folder named turbo.dev in the sites directory, with the files you want to replace (for example, turbo.dev/admin/#.html, turbo.dev/inside/#.html, or m.css, i.png, r.ttf and b.ttf in turbo.dev/admin/). Missing files are served from the copy embedded in Turbo. The embedded pages are sent with a strict Content-Security-Policy that lets them run only their own script and style; a page of your own is sent only with frame-ancestors 'none', so give it a policy in its <head> (for example, <meta http-equiv="Content-Security-Policy" content="default-src 'self'; object-src 'none'; base-uri 'none'">, with its scripts and styles in files of the folder). With the Linux service, turbo.dev is read-only for Turbo and its preprocessors: change it as another user (with sudo, for example). It requires a deep knowledge of the API (API documentation).

Once signed in, depending on the device's screen, the interface looks like the picture. From there you can change the default user and password, or install SSL certificates to connect securely. Each sign-in creates a unique token, kept in a cookie bound to the IP it came from; the session ends after 10 minutes without requests, and 12 hours after the sign-in at most. Over HTTPS, the cookie is __Host-turbo_session, which browsers accept only from the interface's own host. Changing the user or the password, or Close every session, ends every session, and the browser that did it goes on with a new one.

Go on to the Documentation to learn the options of the interface.

Documentation

    1. General settings

      These options ask for the current password in the first dialog (Panel certificate, only to delete the certificate). If you use them for the first time, enter the default password (see Configuration interface). A wrong password counts for the session: the fifth closes it.

      1. Change user

        Sets the new user to sign in to the interface (1 to 24 bytes). It ends every session, and the browser that changed it goes on with a new one.
      2. Change password

        Sets the new password for General settings and for signing in to the interface: 12 to 64 bytes (ñ or é count as 2). It ends every session, and the browser that changed it goes on with a new one.
      3. Close every session

        Closes every session of the interface, in every browser and API client, also the copies of the token of the session that uses it, which goes on with a new session. Useful if you think someone took a session.
      4. Sites directory

        Changes the directory (folder) the web server uses to read, save and serve the files of the websites; the directory must exist. By default, it is the working directory Turbo runs from (with the Linux service, WorkingDirectory) or the one in the TURBO_DIR environment variable. The path may be relative to the working directory or use the {TURBO_CURRENT_DIR} variable, and it is saved as written (so the configuration can be moved to another machine).

        If the new directory has a configuration file, it is applied whole, and the answer says what changes of Where the panel answers and of the credentials. If it has none, the settings in use are kept (general settings, credentials, denied IPs, responses and replacements), and written there when the configuration is saved. Turbo checks everything before changing anything: if the configuration file there can't be used, or leads to a directory that doesn't exist or can't be read, the change is refused and everything stays as it was. After the change, the interface reloads.

        When the configuration is saved with another sites directory, Turbo leaves in the starting directory a configuration file that only points to the new one, to read it from there when it runs again (if there was a whole configuration, it first keeps a copy: turbo.config.<date>.bak). Turbo follows at most two directories counted from the starting one, at the start and in every reload. A configuration file that only points to its own directory, or to one that doesn't exist or can't be used, stops Turbo from starting: restore one of its .bak copies, or make that directory available again.
      5. Where the panel answers

        Limits the interface to the given hosts and networks (CIDR, such as 192.168.1.0/24), separated by commas (up to 32); with both kinds, a request needs one of the hosts and one of the networks. Otherwise it answers with status 404. Empty or * (the default): no restriction. With networks and no host, the interface answers only on an IP address or on localhost, never on a name (a page whose name resolves to Turbo could reach it from the browser of someone in those networks): to sign in by a name, add it. Recommended setup: a host of its own for the interface, one that serves no site, together with the networks it is managed from; Turbo refuses a host that serves a site (directly, through a wildcard or as an alias), and a new site, subdomain or alias that would serve that host. The host is chosen by the client: it gives the interface an origin of its own, but only the networks limit who reaches it. On a host of this option, everything other than the interface's own pages is sent unable to run scripts.
      6. Panel certificate

        Runs Certbot, if it is installed, to request an SSL certificate for the host names of Where the panel answers (IP addresses are left out). It needs an e-mail and takes an optional DNS adapter (dns-<provider>); without an adapter, Certbot validates over HTTP on those hosts, where Turbo answers its challenges (/.well-known/acme-challenge/). The e-mail and the adapter are saved in the configuration. While Certbot works, the option shows (in process), and with the certificate in use, (active); a click then offers to delete it, with the current password. Turbo renews it like the sites' ones (see Create SSL).

        The certificate is kept in the turbo.panel folder of the Sites directory (fullchain.pem and privkey.pem). You can also put those files there by hand: Turbo reads them again when they change, but doesn't renew them. The turbo.panel folder is never a site and nothing is served from it. For the names it covers, this certificate takes priority over the sites' ones.

        With a certificate that covers its host and HTTPS open, the interface redirects HTTP requests to HTTPS (status 301, or 308 to keep the method and body of a POST) and, over HTTPS, on a host of Where the panel answers, sends the Strict-Transport-Security header (one year).
      7. Save configuration

        Creates a file (turbo.config) with the whole configuration of the web server at that moment, the user and the password hash included, in the Sites directory. The file is replaced at once (if anything fails, the previous one stays), and a copy is kept first in these cases: if it was from an earlier version of Turbo (turbo.config.v1.bak), if it wasn't valid JSON (turbo.config.invalid.<date>.bak), or if it changed outside Turbo since Turbo read it (turbo.config.<date>.bak). The copies are written to disk before the file is replaced. If the file is from a later version of Turbo, saving would lose its new settings: the interface asks you to confirm.

        If the file isn't valid JSON at startup (after a manual edit, for example), Turbo doesn't start, so as not to lose the configuration (nor go back to the default password): it shows the file, the line and the column of the error, that line with a mark, and the .bak copies there are, to fix it or restore one. Nor does it start if the file can't be read, if its Where the panel answers, its user or its password can't be used, if a site or one of its lists isn't a JSON object, or if a list is written directly in a site, outside its "" section; and it says why. If the file breaks while Turbo is running, the configuration in use is kept and the same message goes to the log. A single setting that can't be applied (out of range, or of another type) doesn't stop Turbo: its default is used, with a warning in the log.

        If you edit the file by hand while Turbo is running, Turbo checks it every 30 seconds and, when it changes, applies it whole and at once: what isn't in the file any more (a header, an alias, a preprocessor, a denied IP, etc.) stops applying, and changes made from the interface and not saved are lost. The certificates in use keep answering. Entries are applied in a fixed order: when two clash (for example, R. www and R. root both on, the same extension written as PHP and php, or an alias in two sites), the first wins (with the two redirections, R. root), with a warning in the log. A site that the file names only through its subdomains, or as {} or null, is served as one found on disk, with index.html as its index. There is an example turbo.config in the repository.

    2. Time for each request

      These options set the times allowed to process or answer the requests the web server receives. They can be given in milliseconds (ms), seconds (s) or minutes (m), and ask for the current password. A disabled limit (0s) lets a client hold a connection, or keep a preprocessor running, as long as it wants: Turbo warns about it at startup and when it is saved from the interface.

      1. Header read

        Time limit to read the first structural data, the headers, of each incoming request. Past the limit, the connection with the client is closed. With 0s, the value of Total request read is used. Allowed values: from 50 ms to 7.5 minutes, and no more than half of Total request read when that has a limit.
      2. Total request read

        Time limit to read what follows the headers of each incoming request, such as file uploads. This limit starts with the Header read. Past the limit, the connection with the client is closed. To disable it, enter 0s. Allowed values: from 100 ms to 15 minutes.
      3. Response write

        Time limit to answer each request. Past the limit, the response is cut and the connection is closed. It also limits how long preprocessors run. If a preprocessor goes past it, the client gets status 504, and the preprocessor is stopped together with the processes it started (its process group; on Windows, its Job Object), also when the client disconnects first. To disable it, enter 0s. Allowed values: from 100 ms to 30 minutes. Apart from this limit, an HTTP/2 connection where nothing can be written for 30 s is closed.
      4. Idle connection close

        Time limit to wait for the next request on an open connection. Past the limit, the connection is closed. With 0s, the value of Total request read is used. Allowed values: from 100 ms to 5 minutes.

    3. Request rate

      These options set reference time windows and the number of requests that, within them, the web server accepts from each client (IP). Each client is an IPv4 address or, in IPv6, a /64: all its addresses count as one client. Past the limit, the client is blocked for 5 seconds: its requests get status 429 with the Retry-After header (seconds left), and its new connections are closed. Turbo keeps up to 200,000 clients; beyond that, until it forgets the old ones, a new client shares the count of its network (an IPv4 /24 or an IPv6 /48, then a /16 or a /32), without affecting the clients already known. The limit for all the requests of the server is another option, Global request limit, off by default. They ask for the current password.

      1. Request counting window

        Reference time window to count the requests of each client, window after window, up to Maximum requests per interval. The counter grows with each request and starts again after the Counter reset time; what a client doesn't use in one window it can use in a later one, until that reset. Enter the number of milliseconds without ms, from 10 to 50000 (default 1000).
      2. Maximum requests per interval

        Maximum number of requests accepted per Request counting window. Past the limit, the client is blocked for a while. Enter a number greater than 0 (default 100), no greater than the Request counting window (in milliseconds), and such that the window divided by this number is at most 66, so that the interface keeps working (with 1000 ms, from 16 to 1000 requests).
      3. Counter reset time

        Time after which the Request counting window counter of each client starts again. Enter the number of milliseconds without ms, from 1000 to 800000 (default 10000).
      4. Global request limit

        Maximum number of requests per second for the whole server, among all clients: above it, new requests get status 503 with Retry-After: 1, and no IP is blocked. With 0 (the default), there is no global limit. Allowed values: 0, or from 10 to 1000000.

    4. Limits for each request

      These options set how many bytes of the incoming requests the server processes, and how many preprocessors can run at once. They ask for the current password.

      1. Max. size of URIs

        Maximum length of the path of the file, directory (folder) or resource each request asks for, from 40 to 10240 bytes. Past the limit, the request is refused with status 414.
      2. Max. size of headers

        Maximum bytes of the headers of each request, from 600 to 20480. Past the limit, the request is refused with status 431.
      3. Max. body size

        Maximum bytes of what each request carries, such as file uploads or the bodies of POST requests (up to 100 MB). The server doesn't read request bodies by itself; the limit applies whenever they are used (by the interface and by the preprocessors, which get no more than this limit). Past the limit, a request to a preprocessor and a file upload of the interface are refused with status 413. The body of a request to a preprocessor is read whole before it is passed on, up to this limit, and the preprocessor gets it with its size (CONTENT_LENGTH), also when it comes in chunks or over HTTP/2 without Content-Length: all of them take up to 32 MiB of memory, and the rest go to unnamed temporary files (a body of more than 1 MiB, by its Content-Length, goes straight to one). In a file upload of the interface, about 600 bytes per file (what it takes in memory) count besides the content: a file of exactly this size doesn't fit, and if an upload goes over it, the way out is to raise it, as each upload replaces the whole folder.
      4. Concurrent CGI processes

        Maximum number of preprocessors (CGI) that can run at once in the whole server. A request to a preprocessor that finds no free slot within 2 seconds gets status 503 with Retry-After: 2. With 0 (the default), the value is automatic: 4 per CPU, and at least 16. Allowed values: 0, or from 1 to 100000. A preprocessor frees its slot when it ends, even if its client hasn't received the whole response yet (see Add preprocessor); at most a quarter of the slots (at least one; half for an IPv6 /48) may wait for responses of one client that are over their limits.

    5. Add site

      This option creates the directory (folder) structure of each site in the Sites directory. A site can be localhost, an IP (v4) or a multi-level web address, with or without wildcards. IPv6 addresses are not supported. Once added, it shows in the interface, and a click on a site shows its options, its settings and its subdomains. Each site automatically includes the root subdomain (Root), which is the site itself, to configure it specifically. There is no limit of sites or of site data. The public files of each site go inside the subfolder created automatically with the name @. On disk, the server translates the * of wildcard domains to # (e.g. *.org, *.com.es). Site names are in lower case: a site folder with capital letters isn't served, and the log says so once.

      No site (nor any of its subdomains) can be named turbo.dev, turbo.panel, turbo.certificates, turbo.config, turbo.visits or turbo.denials: those are the folders and files Turbo keeps in the Sites directory. Nor can the site c.a.b and the subdomain c of a.b exist together, as they would share their settings: if both are in the configuration or on disk, the first in order stays, with a warning in the log. A site can't have the name of an alias (see Add alias). A site created from the interface starts with the defaults.

      1. Validity of each site

        For the web server to answer the requests of a site, the site must be the server's IP address or a real domain or subdomain that points to the server's IP (through DNS). The server takes the requested name (the Host header) in lower case, without a final dot and without the port, so Example.COM. is served by the site example.com. A name with characters other than letters, digits, . or -, or with a part that starts or ends with -, gets status 404, also on wildcard sites. A Host header that isn't a host (brackets around a name, an IPv6 zone, more than one : outside brackets, a port that isn't 1 to 5 digits) gets status 400, and so does the CONNECT method.

    6. Sites without their folder

      A site whose folder (or its @) disappears, for example during a deploy that deletes and recreates @, an upload by FTP or a network disk that is gone for a moment, isn't served while it is missing, and comes back with all its settings (preprocessors, HTTPS, headers, rewrites, aliases…), also after a restart: they stay in turbo.config. Only a folder that doesn't exist counts, one that its parent folder, listed, doesn't have: when the disk doesn't answer (permissions, I/O, a network share), the site stays as it is. A site of turbo.config whose folder doesn't exist yet gets its settings when the folder appears.

      The interface lists them in this section, which shows only when there is one. Once its folder is gone, the X makes Turbo forget its settings (a site's, together with its subdomains); it asks for the current password and deletes no folder. While a site is in this list, no other site with its name can be created from the interface: deleting the folder of a site doesn't delete the site.

    7. Options for sites and subdomains

      Options available for any site or subdomain.

      1. Add alias

        Adds addresses that lead to the same site or subdomain, without redirecting. A click on an alias deletes it. Over HTTPS, an alias needs an SSL certificate that covers its name; without one, it is still served over HTTP. An alias can't be the name of an existing site or subdomain (it would hide it), and a site can't be added with the name of an alias; if they match when the configuration is loaded, the site wins and the alias is dropped, with a warning in the log.

      2. Create SSL

        Runs Certbot, if it is installed, to request the SSL certificate of the site or subdomain, only when clicked. It needs an e-mail (for Certbot's notices) and takes an optional adapter, which can only be a Certbot DNS plugin (dns-<provider>, such as dns-route53); without an adapter, Certbot validates the domain through the @ folder of the site or subdomain (a request to /.well-known/acme-challenge/ whose file is in @ is served as it is, without rewrites or redirections to www, root or HTTPS). Certbot runs in the background, in the turbo.certificates folder of the Sites directory, and a click on SSL response shows the result or the state of the process (in progress while Certbot works). For a wildcard site or subdomain, the certificate needs a DNS adapter (and the matching Certbot plugin installed). If the site already has a certificate less than 75 days old, Certbot isn't run.

        The sites' Certbot folders share the ACME account of their e-mail, kept in turbo.certificates/_acme-accounts/: issuing certificates for many sites doesn't run into Let's Encrypt's limit of 10 new accounts per IP every 3 hours. Certbot and its hooks get Turbo's environment without the TURBO_* variables.

        Every day (and at startup) Turbo checks the certificates it issued with this option and renews them automatically when they have less than 30 days left; with R. HTTPS on, the renewed certificate is used without a restart. Certificates placed by hand aren't renewed, but Turbo reads the files of a certificate again within 30 s of a change (renewed by another program, for example); a pair that doesn't load yet (a new chain whose key hasn't come) leaves the one in use.

        Which certificate a name gets: when several cover it, the panel's; otherwise the valid one of the site of that name, then any other valid one, and an expired one only if no valid one covers it. The log says when a site's certificate doesn't cover the site's name.

        1. Delete SSL

          Deletes the files of the SSL certificate of the site or subdomain, whatever its age; with no certificate, it does nothing. It asks for the current password. If the certificate is active through R. HTTPS, it stays in memory until that is turned off, even if it has expired.
        2. SSL response

          Shows Certbot's response for the SSL certificate requested for the site or subdomain.
      3. R. HTTPS (redirect to HTTPS)

        Redirects to HTTPS every visit or request over HTTP to the site or subdomain. To turn it on, you need an SSL certificate issued with Create SSL, or valid certificate files (fullchain.pem and privkey.pem) placed in the directory (folder) of the site or subdomain, which are installed on the click. Certificates are installed, updated or removed in real time in memory, without interrupting the open connections or restarting the server. A new certificate is installed next to the old one and replaces it only once the pair loads.

        HTTPS connections use TLS 1.3, and TLS 1.2 only with ECDHE and AES-GCM or ChaCha20-Poly1305 (a very old client that only has CBC suites can't connect). The certificate is chosen by the name the client asks for (SNI): over HTTPS, connections to names without a certificate, and by IP, are refused. The redirection goes to the same name requested, only if a certificate covers it.

        1. No r. HTTPS (no redirect to HTTPS)

          Uninstalls the active SSL certificate of the site or subdomain and removes it from memory, but doesn't delete its files from the directory (folder) of the site or subdomain.
        2. Where to put the SSL certificate files

          The right places for the SSL certificate files in the directory (folder) of each site or subdomain are like these.

          For sites or root subdomains:
          /home/server/example.com/fullchain.pem
          /home/server/example.com/privkey.pem
          For other subdomains:
          /home/server/example.com/subdomain/fullchain.pem
          /home/server/example.com/subdomain/privkey.pem
      4. Upload files

        Deletes everything in the @ folder of the site or subdomain (files and subfolders) and uploads the selected files or directories in its place. Of a selected directory, its content is uploaded: the first segment of each path (the chosen folder) is dropped. The response lists the files dropped: those that would leave @ and, on every system, the names Windows treats specially (ending in a dot or a space, such as CON, NUL or COM1, with ~ followed by a digit, such as the short names INDEX~1.PHP, or with a character Windows doesn't allow: < > " | ? * or control characters), those too long for file systems (a name of more than 255 bytes or a path of more than 1024), and, of a file and a folder with the same name (a and a/b), the second. The upload is subject to Max. body size and takes up to 10000 files. SSL certificates aren't affected, as they are kept apart from the public files. The @ folder is replaced at once at the end: if anything fails, or every file is dropped, it stays as it was. It asks for the current password.

      5. Delete site / Delete subdomain

        Deletes everything related to a site or subdomain, its directory (folder) included. For a site, its subdomains are deleted too, with all their data. For the root subdomain, the option shows as Delete site, as it is the site itself. It asks for the current password. In any case, the configuration file doesn't change until Save configuration is used.

    8. Options for sites or root subdomains

      These options are only for sites or root subdomains: they are set there, although R. root acts on the visits to the www subdomain. The interface doesn't show them on other subdomains.

      1. R. www (redirect to www)

        Redirects the visits or requests to the root subdomain to the www subdomain. While it is on, the opposite redirection can't be turned on. Example:
        Visit: https://example.com
        Redirection: https://www.example.com
        1. No r. www (no redirect to www)

          Turns off the redirection from the root subdomain to the www subdomain.
      2. R. root (redirect to root)

        Redirects the visits or requests to the www subdomain to the root subdomain. While it is on, the opposite redirection can't be turned on. Example:
        Visit: https://www.example.com
        Redirection: https://example.com
        1. No r. root (no redirect to root)

          Turns off the redirection from the www subdomain to the root subdomain.

    9. Add subdomain

      This option creates the directory (folder) structure of each subdomain inside the directory of its site, except for the root subdomain (Root). It can be multi-level (level3.level2.subdomain) and can include wildcards. A subdomain without a wildcard serves only its own host: api serves api.example.com, and deeper levels (x.api.example.com) are served by a wildcard, *.api (or the site's *). Once added, it shows in the interface, and a click on a subdomain shows its options and settings. There is no limit of subdomains or of subdomain data. The public files of each subdomain go inside the subfolder created automatically with the name @. On disk, the server translates the * of wildcard subdomains to # (e.g. *.example.com, *.area.example.org).

    10. Subdomain options

      Options available for any subdomain.

      1. Add MIME

        Replaces the default Content-Type header of the subdomain's files with the given extension by the content entered (4 to 128 characters). An empty extension refers to files without an extension (as in the picture); a lone dot (.) isn't "no extension" and is refused. As a MIME type can make one of the site's files run as a page (text/html, for example), adding and deleting one ask for the current password.

      2. Add header

        Adds the header with the given name and content to the responses of the subdomain's files and preprocessors (not to 404 responses, nor to the redirections of rewrites, HTTPS or www). The name takes letters, digits, - and ., up to 48 characters; the content, up to 512. Adding and deleting one ask for the current password. A Content-Security-Policy added here is sent next to Turbo's, never in its place.

      3. Add rewrite

        Adds a rewrite of the given path of a file, directory or resource (URI), to handle it internally as another given path, without redirecting. The URI doesn't have to exist. The source URI starts with / (up to 128 characters), and the target with /, http:// or https:// (up to 512). Keywords give access to the data of the first URI and of the site and subdomain (useful on wildcard sites or subdomains and for preprocessors); an unknown keyword is refused (in the configuration file, the rewrite is dropped with a warning in the log). The source URI is compared with the decoded request path (/a b matches /a%20b); a source that ends in / also takes the folder without it (/private/ takes /private). The target is a URL path too (a literal % is written %25). If, once the keywords are replaced, the path leaves the @ folder or contains \, the answer is status 404.

        A preprocessor reached through a rewrite whose target has a query string gets the request's query without the parameters that the target's sets, and then the target's: with /x → /app.cgi?role=user, the request /x?role=admin&z=1 reaches it as z=1&role=user.

        To redirect, enter a target that starts with http:// or https:// (in any case; it is saved in lower case) followed by a host, written or given by a keyword: the answer is status 302. A target without a host (https:// alone) is refused, and if the host keyword gives no value when answering, the answer is status 500. If the target has a path or a query string, the redirection goes exactly there; if it is only a domain, the original URI is added to it.

        1. Available data

          Keywords in a rewrite are replaced by their data. They are written like this:
          {KEYWORD}
          The values of FIRST_REQUEST, DIR, FILE, EXT, REWRITE and REWRITE_COMPLEMENT come from the decoded request path, and those of FIRST_QUERY from its query. Each value is inserted encoded for where it goes in the target: in the path, segment by segment, keeping /; in the query string, as one value (for example, / becomes %2F); in the host, so that it can't change the URL. For example, with the source /blog/ and the target /new/{REWRITE_COMPLEMENT}, /blog/a/b?x=1 becomes /new/a/b?x=1. Through an alias of a wildcard site, SUBDOMAIN and SITE hold the pattern (with *); the names of the alias are in the FIRST_ keywords.

          Available keywords:
          1. TURBO_CURRENT_DIR

            The path the websites are served from.
          2. WILDCARD_SITE

            The full web address (subdomain and domain) of the wildcard site it belongs to.
          3. WILDCARD_DOMAIN

            The domain of the wildcard site it belongs to.
          4. WILDCARD_SUBDOMAIN

            The subdomain of the wildcard site it belongs to.
          5. DOMAIN

            The domain of the site it belongs to.
          6. SUBDOMAIN

            The subdomain of the site it belongs to.
          7. SITE

            The full web address (subdomain and domain) of the site it belongs to.
          8. FIRST_DOMAIN

            The alias domain it was reached through.
          9. FIRST_SUBDOMAIN

            The alias subdomain it was reached through.
          10. FIRST_SITE

            The full alias web address (subdomain and domain) it was reached through.
          11. FIRST_REQUEST

            The full path or URI that was rewritten.
          12. FIRST_QUERY

            The query string of the URI that was rewritten.
          13. DIR

            The directory (folder) of the URI that was rewritten.
          14. FILE

            The name of the file that was rewritten.
          15. EXT

            The extension of the file that was rewritten.
          16. REWRITE

            The source URI of the rewrite that matched.
          17. REWRITE_COMPLEMENT

            The rest of the requested URI after the source URI of the rewrite (path and query string). In the path of the target, only the rest of the path, and the request's query string is added to the target's.
      4. Add preprocessor

        Assigns the given preprocessor to every file of the subdomain with the given extension, in any case (.PHP also runs as .php). The preprocessor must handle and answer, through CGI and its environment variables, the requests for the files with that extension.

        PHP: add a preprocessor for the php extension with the path of php-cgi (for example /usr/bin/php-cgi, from the php-cgi package). Turbo sets the REDIRECT_STATUS environment variable, so PHP scripts run without changing php.ini; PHP gets the URL path of the script in PHP_SELF and SCRIPT_NAME, the original REQUEST_URI, and Turbo's temporary folder, where it keeps uploads. Under the reference systemd unit, PHP's default sessions folder (/var/lib/php/sessions) is read-only: point session.save_path to a folder inside the sites folder.

        What the preprocessor gets of the request: headers with _ in their name don't reach it, as in Apache, and HTTP_HOST and SERVER_NAME carry the host as it chose the site (in lower case, without a final dot, and with its port).

        Its response: Turbo frames it: from what the preprocessor writes, the connection headers (Transfer-Encoding, Connection, Keep-Alive, Upgrade…), a repeated Content-Length and headers with control characters are dropped. The output waits for a slow client in memory (up to 1 MiB per response and 64 MiB in all) and then in unnamed temporary files of 32 MiB, each deleted as soon as it is sent (up to 256 MiB per response and 1 GiB in all), so the preprocessor frees its slot when it ends; one client may take a quarter of those totals. Once a preprocessor that goes on has been quiet for 100 ms, what it wrote is sent, and from then on what it writes is sent at once: server-sent events, progress and long polling work. One that ends sooner is sent whole, with its length.

        The preprocessor path takes up to 128 characters and must exist when it is added; the dx> prefix isn't available. As a preprocessor runs programs on the server, this option asks for the current password. Deleting one (the X next to it) asks for it too: without its preprocessor, the files of that extension would be served as text, their source code included. If the binary is gone later (for example, when the saved configuration is loaded), the files with that extension answer status 500 instead of being served. So does a preprocessor of the configuration file that can't be used (an empty or too long path, a wrong extension, another prefix, a missing binary, control characters): it is kept, with a warning in the log, and its extension answers status 500; the files are never served as text.

        How many preprocessors run at once is limited by Concurrent CGI processes, and how long, by Response write. A preprocessor ends when its client goes away, and when Turbo stops, after 10 s, with whatever it started.

        IMPORTANT: if preprocessing isn't set up on the subdomain, the files meant for dynamic use (preprocessed, usually code) are served as static files (plain text, etc., depending on the MIME type), which can expose those files and their source code.

      5. Add index

        Adds the default file that answers the requests for directories (folders). The file has to exist in each directory. With more than one, they are tried in the order they were added. New sites and subdomains start with index.html. A request whose path ends in /index.html is redirected (status 301) to its directory (./).

    11. Log files

      To log the blocks of the rate limiter and of the failed sign-in attempts (one line per block, not per refused request; those refused by Global request limit aren't logged), create an accessible file named turbo.denials, and to log every access to every file or route of the server, create another one named turbo.visits, in the Sites directory. Turbo writes to these files only if they exist; it notices them (or stops using them once deleted) in its periodic check, every 30 seconds, and also notices then a file rotated by renaming it (logrotate's create). Fields with spaces or control characters are written quoted and escaped. As they can grow very large, don't create these files if you don't need logs.

      Turbo's other messages (startup, configuration, sites, certificates, errors) go to standard output (stdout) or the console, with a level (INFO, WARN, ERROR) and the date and time; with the Linux service, to the journal (journalctl -u turbo). The errors of the connections (failed TLS handshakes, clients without SNI, malformed HTTP/2 frames…) and those of the preprocessors whose client goes away are grouped by kind: the first of each kind is logged at once, and then at most one line a minute with the count and the last one, so that they can't fill the log.

      turbo.visits doesn't log the requests refused by the limiters (429, 503), the connections closed on arrival from a blocked IP, nor the malformed or too large requests refused before they are processed (400, 414, 431); the blocks, those of failed sign-in attempts included, are in turbo.denials.

      Privacy: for every request it processes, turbo.visits logs the client IP, the date (UNIX timestamp), the method, the host and the full URI with its query string, the requests to the interface included (the interface sends its data, such as the current password, in the request body, which isn't logged). An API client that put the password or other sensitive data in the URL would leave them in this file: send them in the body, as the interface does. The interface session doesn't appear in it, as it travels in a cookie. Treat this file as personal and sensitive information: restrict its access, and delete or rotate it as you need.

    12. Add denied IP

      Blocks specific IP addresses (IPv4 or IPv6) by hand, at once. Enter the IP address and the date, as a UNIX timestamp, until which it stays blocked. While the block lasts, its requests get status 429 (with Retry-After) and its new connections are closed. An IPv6 address blocks its whole /64, the client that the limits of Request rate count (its addresses change by themselves). Loopback addresses (127.x.x.x, ::1 and any other of ::/64, which holds ::1) and the IP the interface is used from (in IPv6, its /64) can't be blocked. Once the date passes, the server unblocks it by itself. To remove the block earlier, click the X of the IP in the list.

    13. Add HTTP code response

      Customizes the response, a text or HTML template, that the server sends for a given HTTP error status code (codes from 400 to 599, or 0 for the general default response, Default in the list). The {TURBO_RESPONSE_CODE} tag inserts the error code in the response. If the template starts with <, it is served as HTML; otherwise as plain text, where \n is a line break. It takes up to 2048 characters. As a template is the error page of every site, adding and deleting one ask for the current password.

      An error page never runs scripts: on every host, it is sent with a Content-Security-Policy without them and with sandbox, so it can't redirect by itself (meta refresh), send forms or open windows either. External styles, fonts and images are blocked too: a template can use its own styles and data: images.

    14. Add character replacement

      Sets global rules to replace special characters in the values the interface sends to the server (rewrites, MIME types, headers, etc.); they don't apply to the URIs of the requests the server receives. Characters that could clash with URL delimiters (for example: ; with -.-, # with -,-, or & with -_-, the three fixed ones) are sent as safe strings, and Turbo restores them on arrival. A replacement is for 1 to 4 bytes, without letters or digits, and its string has 2 to 16 characters. Turbo doesn't restore them in the options that ask for the current password, nor in the site and the subdomain of any option. Adding and deleting one ask for the current password. No value may contain control characters (response templates may contain line breaks and tabs).
